Part A

Platform — the shared spine every module inherits

Decisions made once here are inherited by Delivery Challan and every future module (QR, courier files, reward letters…). We build shared runtime primitives, not a speculative plugin framework: modules stay decoupled by ownership and code review, not by heavyweight machinery.

A1

Identity & access

Authentication — Firebase Auth, email/password

  • GCP-native (same cloud as everything else), managed — we never store or hash passwords ourselves.
  • Every API request verifies the Firebase token server-side; the provider is the sole authority for "is this account active."
  • Offboarding: disabling a user in Firebase instantly kills access. A valid token with no active RBAC row is denied, never auto-provisioned. Short token lifetime; a periodic reconcile flags RBAC rows with no live account. (No Google Workspace = no central directory, so this runbook matters.)

Authorization — RBAC in Postgres

  • Two axes: a role (Admin · MIS · Operations · Finance) governs what actions you can do; a per-user module-access list (explicit grants, not role-derived) governs which modules you can open. Checked by can(user, action, resource?) + can_access_module(user, module).
  • User Management screen (Admin): create/invite a user by email, assign their role + tick the modules they can access, enable/disable. Users are provisioned via the Firebase Admin SDK and set their own password through an invite/reset link — the admin never handles passwords. Every user/role/access change is audited.
  • The resource arg is shaped in now so per-consignor/brand segregation is a later toggle, not a rewrite. Default: all staff, all entities. (A full per-action permission matrix stays out of scope — module-level access is the granularity you asked for.)
Panel note

All three reviewers agreed the provider choice is secondary; the real work is server-side token verification + Postgres RBAC as the "active" authority + a documented offboarding path. That's what's specified here.

Admin-only actions (hard-coded)

Void a challan · override the duplicate-number block · bulk-accept validation warnings · edit master data · change settings · seed a number series · User Management (create/invite users, assign role + module access, enable/disable). Every one writes an append-only audit row (§A5).

A2

Data & module boundary

  • One PostgreSQL database, one schema. Platform tables unprefixed (user, role, audit_log, file, setting, doc_sequence); module tables prefixed (challan_batch, challan_document, challan_line).
  • Modules are decoupled by ownership convention + code review, not by database walls. Cross-module reporting stays a plain join instead of a growing UNION across schemas.
  • One migration chain (Alembic).
  • Module registration is a convention: each module exports registerModule({ nav, routes, permissions, migrations }). This is a static object the app composes at build — not a runtime plugin loader.
Reversed from v1

Schema-per-module was overruled: it buys isolation a single-tenant, ~50-user app doesn't need while taxing cross-module reporting and migrations. Table prefixes give the same decoupling for free.

A3

Shared runtime primitives

Built once, consumed by every module — real reusable code, so modules don't each hand-roll uploads, polling, and audit calls:

PrimitiveWhat it gives every module

Deliberately NOT built: schema walls · a runtime plugin loader · registries-as-frameworks · a permissions admin UI · micro-frontends. The right abstraction for module #2 is extracted after it exists.

Where the two reviewers met

The platform lens wanted shared runtime primitives; the pragmatist wanted near-zero speculative infra. They agree on this list — cheap, needed by Module #1 anyway, and nothing whose only justification is a module that doesn't exist yet.

A4

Jobs & async

  • In-process background task writing status rows to Postgres; the SPA polls job status for the progress bar. No queue infrastructure in v1.
  • Justified by the numbers: HTML→PDF renders a one-page challan in ~50–200 ms, so 1000 docs ≈ 2–5 min — well inside Cloud Run's 60-minute request window.
  • An idempotency key on batch creation makes double-submits and retries no-ops (this is a correctness requirement, not an optimisation — see §B3).
  • Guardrails: bounded render concurrency + per-job memory ceiling; Cloud Run min-instances ≥ 1 to avoid cold-start latency on a spiky internal tool.
  • We add Cloud Tasks only the day a batch genuinely can't finish in one window — it will fail loudly first.
Module 2 exception

Self-hosted OCR + image processing is CPU/memory-heavy, so the Expense module runs on a queue-backed worker tier (Cloud Tasks + a separately-scaled worker) rather than the in-process model. The jobs primitive is the shared seam either way.

A5

Audit, security & compliance

  • Append-only, hash-chained audit log. The app DB role has no UPDATE/DELETE on it. Captures actor, IST timestamp, before/after, reason, IP, downloads, overrides, seeds — tamper-evident for a legal register.
  • PII protection. Names, addresses, phones, GSTINs. Structured logging redacts PII by default — we log row ids, not row contents.
  • Retention. Generated GST documents are write-once and retained ~6–8 years; the raw uploaded Excel (the rawest PII) gets a short lifecycle. Documented against India's DPDP Act storage-limitation expectation.
  • Downloads stream through the authenticated API with an authorization re-check + audit on every fetch — no long-lived signed URLs handed to the browser.
  • Renderer is egress-locked (no network — blocks SSRF to metadata endpoints), HTML autoescape on, and all cell values are passed as bound data, never concatenated into a template (kills template-injection from a malicious Excel cell). Leading = + - @ escaped on any Excel export.
  • Secrets in Secret Manager. Observability: structured logs + error tracking (Sentry) + trace continuity across the background boundary. Golden-file PDF regression tests in CI so layout drift fails the build.

A7

Document Intelligence — a reusable, swappable service

Extraction (OCR + field parsing) is built as a standalone platform service, not baked into any module — because you intend to reuse the capability elsewhere. It owns a clean, product-agnostic contract; any module (or later, any product) consumes it over HTTP.

POST /extract   { document, doc_type }
   → { fields, confidence_per_field, raw_text, review_needed }

Swappable engine — the escape hatch

  • Internally, an ExtractionEngine interface with pluggable implementations: SelfBuiltEngine (layered — searchable-PDF text → OCR → rule-based → optional vision-LLM fallback) and a DocumentAIEngine adapter.
  • Every engine maps into your canonical field schema — consumers never see an engine's raw shape, so switching engines changes nothing upstream.
  • Decision: your SelfBuiltEngine is primary from day one (justified by a real second use case for the capability); the DocumentAIEngine is the wired-in backup / escape hatch, not the initial engine. Because every engine maps to the canonical schema, falling back is a config flip — fully reversible.
  • Originals stay in GCS, so any engine can re-extract the back-catalogue later — no historical lock-in.

Build guardrails (non-negotiable, from review)

  • Engine-neutral canonical schema, up front — per-field envelope {value_normalized, value_raw, confidence, source_engine, page, bbox|null, status}; money = BigInt-paise + rounding line; line items first-class; document/page model; calibrated confidence contract; schema version.
  • Evaluation harness before the engine — labelled gold set + field-level scoring (exact / numeric-tolerance / date-normalized). Without it you can't prove accuracy or safely swap; checksums validate only ~half the fields (not date, number, or vendor).
  • Invert the pipeline — Vision/LLM primary for non-text-layer docs; rules as validator/normalizer, not primary parser.
  • HEIC + quality gate (deskew/denoise, fail-closed on unreadable) · dedup key (GSTIN + invoice# + date + total, plus perceptual hash) · every human correction feeds the eval set.
Why a platform service, not module code

You chose to build and own extraction to reuse it later. The durable asset is the service + its API + your canonical schema; the engine underneath is an implementation detail you control and can replace. First consumer: the Expense & Invoice module. When a second, external consumer (a client app) arrives, it graduates to its own platform-services home rather than being reached into inside the internal OpsHub project — the versioned contract makes that a day of work.

Honest note on accuracy

Document AI would out-score a hand-built pipeline on raw extraction from messy scans, out of the box. Built well — validation (GSTIN checksum, tax-sum reconciliation) + confidence scoring + a review queue + LLM fallback for hard cases — accuracy is good and, crucially, wrong reads are caught, not silently saved. At ~100 invoices/month the residual gap is a handful of extra reviews.

B3

Numbering & integrity — the load-bearing spec

Document number formatGIF/DC/26-27/L/000189
  • FY = Indian financial year (Apr–Mar), computed in Asia/Kolkata everywhere; we store both UTC and the IST business date the number was issued under.
  • Independent counter per (series × FY), resetting each April. Series: one shared L by default; Admin can add more.
  • Cutover seed: a one-time, audited, admin-signed action records the last manual number (e.g. L / 26-27 = 188), with a guard so the first system number can't precede it.
Why this is its own section

Every reviewer independently escalated numbering as the highest risk and the real IP — a duplicated live GST number is a compliance failure that's unfixable once documents leave the building. It's a platform service; every future numbered-document module inherits it.

Reserve-before-generate

  1. Validate the whole batch first — no numbers are touched until validation passes.
  2. In one transaction: lock the counter row (SELECT … FOR UPDATE), reserve N numbers, write documents as RESERVED, bump the counter.
  3. Generate PDFs; mark each GENERATED (per-document idempotent — skip any already generated).
  4. On failure → job FAILED; reserved numbers are consumed, never recycled (gaps are legal and explained by FAILED/VOID status).

Integrity controls (the defects the security review found, and their fixes)

RiskSevControl

Double-submit / retry double-reservescritIdempotency key on batch creation; a retry returns the existing reservation

Modes: continue-from-last (default) and custom-start ship in v1. deferred read-from-Excel (mode 3) moves to phase 2 — it's the highest collision risk and ships only once the unique-constraint + in-lock validation is proven.

B4

Validation

Hard errors block generation

  • Missing mandatory: Ship-To Name / Address / State, Product Description, HSN, Qty, Amount.
  • Ship-To State has no matching Brand-State registration (consignee GSTIN can't be derived).
  • A Challan Ref group with no line items; unparseable Qty.

Soft warnings accept / reject each

  • HSN → GST-rate mismatch vs saved history (rate only — same HSN carries many descriptions).
  • Amount sanity: where Qty & Rate are numeric, warn if Amount ≠ Qty × Rate × (1 + GST%); skipped when Rate is blank/text (e.g. "Gift").
  • Duplicate-dispatch: same Ship-To + same products on the same date. · GSTIN checksum anomalies.

e-way flag informational — challans over eway_threshold (admin-set, default ₹50,000) are flagged "e-way bill required." Accepted warnings are logged as ValidationOverride. Every issue is exportable as a plain-English .xlsx (Row · Ref · Field · Severity · Issue · Suggested fix · Your value · Expected).

B5

Rendering — HTML → PDF

  • Template is HTML/CSS with a repeating line-item loop, rendered by WeasyPrint in-process. Versioned in git, snapshot-tested, deterministic — no LibreOffice.
  • One PDF per challan (multi-line). Naming: GIF_DC_26-27_L_000189.pdf. Copies (Original / Duplicate / Triplicate) are an admin-enabled toggle.
  • Egress-locked renderer, autoescape on, cell values bound as data (§A5).
Reversed from v1 — unanimous

All three reviewers voted HTML→PDF over DOCX/LibreOffice: lighter, testable, deterministic, and it removes the Jinja-in-DOCX template-injection class. LibreOffice was called an "operational tarpit."

B7

Void & lifecycle

Document: RESERVED → GENERATED → VOID.  Job: PENDING → GENERATING → COMPLETED / FAILED.

Void admin — reason mandatory, audited; the number is retained, never reused. A reconcile sweeper resolves orphaned RESERVED rows. This is the correct handling of a cancelled dispatch under gap-tolerant numbering.

Project topology & isolation

OpsHub runs in its own GCP project (same billing account → one consolidated invoice + a per-project budget alert to catch spikes). Three projects, each isolated by risk class — not one per app, not one shared blob:

ProjectRisk classHolds
LoyaltybaseExternal · money-criticalMulti-tenant loyalty (existing)
OpsHubInternal staffDelivery Challan · Expense · Document Intelligence
gifsy-clientsExternal · client-facingMulti-tenant app + bespoke client apps (future)

What crosses the boundary — code & services, never servers

  • Isolated per project: project, DB instance, buckets, service accounts, auth. OpsHub's DB is never on the same instance as Loyaltybase's money path or the internet-exposed client apps.
  • Reused as versioned code: Terraform modules, CI/CD template, auth/RBAC/audit libraries, log conventions.
  • Reused as an authed API: the Document Intelligence service (cross-project OIDC).
Cross-service hardening (from review)

Where services or stacks meet: service-to-service auth (GCP OIDC) · a versioned extraction API (OpenAPI/protobuf, generated clients) · W3C trace propagation across the boundary · GCS bucket/IAM isolation · idempotent extraction ingest · conformance test-vectors so the hash-chained audit + FY-numbering behave byte-identically across the Python and Node stacks.

The rule

Audience / risk class = a project boundary. Know-how crosses it as libraries; capabilities cross it as authed API calls. Databases and servers don't cross it.

Cost & scaling

  • Separate GCP project, same billing account → consolidated invoice + a per-project budget alert that catches any spike (runaway OCR/LLM, storage) immediately.
  • Cloud Run scales to zero (~15s cold start; fine for internal background work). API + OCR worker.
  • Database — Option B: Cloud SQL can't scale to zero, so OpsHub runs one small instance (smallest tier, single-zone, no HA) hosting separate prod + non-prod databases. Backups + point-in-time recovery kept. Never co-located with Loyaltybase or the client apps.
  • Extraction: self-built OCR ≈ ₹0/page; Vision within free tier; fallback trivial at ~100 invoices/mo. The real cost is build engineering, not cloud spend.
